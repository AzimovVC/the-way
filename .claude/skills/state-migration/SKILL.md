# Изменение схемы сохранённого состояния

## Чем это опасно

Всё состояние живёт в localStorage под ключом `the-way:v1` в конверте
`{ version: 1, state }`. Бэкенда нет — **localStorage и есть единственная копия данных
пользователя**. Потерянный прогресс не восстановить ниоткуда.

Сегодня [appStorage.ts](../../../src/storage/appStorage.ts) на любое несовпадение молча
возвращает пустое состояние:

```ts
if (parsed.version !== 1 || !parsed.state) return createEmptyState()
```

Механизма миграции нет. Значит:

- **Поднять `version` без миграции = стереть прогресс всем пользователям.**
- Добавить обязательное поле, не подняв версию, — оставить старые записи с `undefined`
  там, где типы обещают значение. TypeScript это пропустит: содержимое localStorage
  приводится к типу через `as`, без проверки.

Оба исхода тихие. Ни ошибки, ни предупреждения — просто пустой путь при следующем запуске.

## Как решать

**Необязательное поле** (`newGoalIds?`, `milestonesReached?` — уже так сделаны):
версию не трогаем, читатели обрабатывают `undefined` (`?? []`). Самый дешёвый путь —
предпочитайте его, когда он подходит.

**Обязательное поле, переименование, смена формы:** нужна миграция.

1. Поднимите `version` до 2, расширьте `StoredEnvelope` (версия — объединение: `1 | 2`).
2. Напишите чистую функцию `migrate(envelope): AppState`, которая проводит запись по
   цепочке версий вверх. Держите её в `src/storage/` — она заслуживает тестов.
3. Переделайте `loadState`: **мигрировать, а не сбрасывать.** `createEmptyState()`
   остаётся только для случая «данных нет» и «JSON не разбирается».
4. Сохраните после миграции, чтобы она не проигрывалась при каждом запуске.
5. **Тест на реальном снапшоте старой версии.** Возьмите настоящий JSON из localStorage
   (`localStorage.getItem('the-way:v1')` в браузере), положите как фикстуру и проверьте,
   что дни и цели после миграции целы.

## Чек-лист правки

- [ ] Поле правда нужно в **сохраняемом** состоянии? Производные величины
      (`pathAngleDelta`, `columnDriftX`, `colorTier`) считаются из истории через
      `applyPathGeometry` — их незачем расширять новыми хранимыми полями.
- [ ] Можно обойтись необязательным полем?
- [ ] Если нет — версия поднята **и** миграция написана.
- [ ] Есть тест со снапшотом предыдущей версии.
- [ ] `createEmptyState()` обновлён, если поле обязательное.
- [ ] Затронутые потребители: [AppStateContext.tsx](../../../src/state/AppStateContext.tsx),
      `domain/dayLifecycle.ts`, `domain/freezes.ts`, `domain/goalManagement.ts`,
      `domain/milestones.ts`, `domain/analytics.ts`.
- [ ] `npm run test && npm run build`.

## Что ещё стоит знать про этот слой

- Запись дебаунсится на 400 мс; `beforeunload` и `pagehide` дожимают её принудительно.
  Добавляя новый путь выхода из приложения, зовите `flushPendingSave()`.
- `AppStateContext.setState` пишет в хранилище **всегда**. Отдельного «сохранить» нет —
  и не надо его добавлять.
- Восстановление пропущенных дней (`reconcileMissedDays`) и авто-заморозки выполняются
  один раз при монтировании провайдера. Новое поле, которое должно появляться у каждого
  дня, нужно проставить и там — иначе задним числом созданные дни будут отличаться от
  созданных обычным путём.
- Ключ `the-way:v1` содержит версию в имени. Если вы когда-нибудь смените сам ключ,
  старый останется в браузере мусором — читайте старый, мигрируйте, удаляйте.
- Настройки DevPanel (`pathTuning.ts`) лежат в localStorage **отдельными** ключами и к
  этому конверту отношения не имеют.
